---

Encerramento de sessão. Faça, nesta ordem:

1. Levante o que mudou nesta sessão: `git status --short`, `git diff --stat`, e `git log --oneline` desde o início da sessão (ou desde o commit que `ESTADO_SESSAO.md` §1 registrava como mais recente, se ainda estiver visível no histórico da conversa).
2. Releia rapidamente `CLAUDE.md` §Comandos padrão e a seção correspondente de `docs/governanca/GOVERNANCA_DO_PROJETO.md` para confirmar que a atualização abaixo segue as regras vigentes — não é preciso reler o restante desses arquivos.
3. Reúna, a partir da conversa desta sessão: decisões tomadas, arquivos alterados, commits feitos (se houver), tarefas concluídas, pendências novas ou resolvidas, riscos novos ou mitigados. Só pergunte ao usuário se faltar uma informação crítica para fechar o snapshot (ex.: qual é a próxima tarefa) — nunca faça uma lista longa de perguntas.
4. **Antes de tocar em `ESTADO_SESSAO.md`, identifique o arquivo de log da fase corrente em `docs/_workspace/logs/`** (o mais recente por data/nome — ver "Links para logs relacionados" na versão atual do `ESTADO_SESSAO.md`). Mova para lá, por acréscimo ao final (nunca reescrevendo o que já existe), qualquer conteúdo narrativo da sessão que não caiba nas 7 seções fixas do passo 5 (detalhe de achados, riscos extensos, checklists granulares, prompt de handoff, transcrição de decisões). Se o arquivo de log atual já tiver ~1500 linhas ou mais, encerre-o (Resumo da fase, Resultado, Decisões tomadas, Commits relevantes, Próxima fase) e crie um novo arquivo de log para a fase corrente/seguinte em vez de continuar acrescentando ao antigo.
5. **Reescreva por completo** `docs/_workspace/ESTADO_SESSAO.md` (nunca acrescente — é sempre um snapshot, nunca um diário de bordo) com **apenas estas 7 seções fixas**: Situação atual, Objetivos, Próxima missão recomendada, Pendências/bloqueios, Últimos commits relevantes, Arquivos importantes, Links para logs relacionados. Alvo: no máximo ~300 linhas. Qualquer detalhe que não caiba objetivamente nessas seções vai para o log (passo 4), não para este arquivo.
6. Se algo desta sessão for uma decisão de arquitetura, de domínio, ou uma mudança de estado de SPEC relevante para o histórico de longo prazo (não só para o próximo `/comecar`), registre também uma entrada correspondente em `docs/_workspace/TASK_ROUTER.md`, seguindo a convenção já usada lá (seção datada, apenas acrescentada ao final) — `ESTADO_SESSAO.md` é o snapshot rápido, `docs/_workspace/logs/` é o histórico narrativo de sessão, `TASK_ROUTER.md` continua sendo a fonte única de estado e dependências entre SPECs.
7. Se — e só se — esta sessão concluiu um marco (fim de fase, refatoração grande, migração, release): acrescente uma entrada em `docs/handoff/README.md`, seguindo exatamente o formato oficial já usado lá. Caso contrário, não toque nesse arquivo.
8. Nunca altere SPEC, ADR, arquitetura ou PRD como parte do encerramento — isso exige autorização explícita do responsável do projeto e um fluxo próprio (Auditoria → Plano → Execução → Validação → Commit), não o `/fim`.
9. Não crie nenhum outro arquivo de encerramento (relatório de sessão, changelog avulso, etc.) além do log de fase em `docs/_workspace/logs/` já previsto no passo 4 — a atualização de `ESTADO_SESSAO.md` (e, quando aplicável, do log de fase, `TASK_ROUTER.md`/`handoff/README.md`) é suficiente.
10. Reporte ao usuário, em poucas linhas, com esta estrutura: **Sessão concluída** (resumo do que foi feito) · **Arquivos atualizados** · **Pendências** · **Próxima missão sugerida** · **Tempo estimado da próxima missão** (quando for possível estimar).
